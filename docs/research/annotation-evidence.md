# Annotation UX evidence base (text classification + span labelling)

Scope: what the literature and credible engineering write-ups say about annotation speed and quality, applied to quet-web: one pass per record, a type (8 classes), 1-2 named spans (`target`, `value`), a record status (complete / uncertain / skipped), optional model proposals, 150 short Vietnamese finance notes, outside collaborators, desktop-first.

Conventions: every claim links to the source that owns it. `[INFERENCE]` = my reasoning, not a finding of the cited source. Numbers are quoted from the source text I opened; where I could not open a paper (paywall/403) I say so in "Limits" and cite nothing beyond what I read.

Context from the user (via Main): the six complaints about the current screen are (1) too much on screen, (2) marking spans is fiddly (drag/click, which field a selection goes to, Tab between target/value), (3) picking the type is slow (8 long definitions in a side panel, keys hard to remember), (4) unclear what is saved (draft vs saved, what Enter does, when it advances), (5) confusing keyboard scheme (`x n c m tab [ ] z \`), (6) looks bad. The user likes **Label Studio**. Section 13 grades Label Studio's pattern against the evidence.

## 2. Keyboard vs mouse

* **Model-based numbers (strong physics, not annotation-specific).** The Keystroke-Level Model gives K (keypress) 0.28 s (0.20 s skilled typist), P (point with mouse) 1.1 s, BB (click) 0.2 s, H (home hand keyboard<->mouse) 0.4 s, M (mental act) 1.35 s ([Kieras, KLM description](https://www.cs.umd.edu/~golbeck/INST631/KSM.pdf)).
  [INFERENCE] Picking a type by mouse costs P+BB ≈ 1.3 s of motor time (plus H 0.4 s each time hands cross between devices); by a number key ≈ 0.28 s. Marking one span by mouse drag ≈ H + P + press/release/drag ≈ 1.7+ s; a keyboard span command of 2 keys (start word number, end word number) ≈ 0.56 s. A record with type + 2 spans + save costs roughly 4-5 s of pure motor time when spans are dragged, vs about 1.5 s fully keyboard. Against per-record times of 5-10 s (see section 10) that is the single largest controllable cost.
* **Keyboard shortcuts are undiscovered unless surfaced.** Experienced users often do not use keyboard commands even though they are more efficient ([Lane, Napier, Peres, Sándor 2005, IJHCI](https://www.tandfonline.com/doi/abs/10.1207/s15327590ijhc1802_1), summarized in [Peres et al. 2005](http://chil.rice.edu/research/pdf/Peresetal2005.pdf)). Design response: show the key on the control it triggers.
* **How real tools expose keys for many labels.** Prodigy maps digits `1-9` to options 1-9, `0` to 10, `shift+num` to 11-20, with `a`/`x`/`space` for accept/reject/ignore, `backspace` for undo and `h` for instructions ([Prodigy web app docs](https://prodigy.ai/docs/api-web-app)). Label Studio auto-assigns hotkeys to choices in visible order ([Choices tag](https://labelstud.io/tags/choices)). Both use *positional digits*, which is exactly what quet-web's `1`-`9` already does.
* **Controlled keyboard-vs-mouse annotation study:** none found in ACL Anthology / CHI searches. [UMR-Writer 2.0](https://aclanthology.org/2023.law-1.21.pdf) built an index-based keyboard interface (each token gets a 1-based index typed in commands) but reports no timing in the part I read. **Weak evidence**: rests on KLM + vendor practice.

## 3. Span selection: token vs character, drag vs alternatives

* **Snapping to tokens is standard practice for speed.** Prodigy: pre-tokenizing lets the selection "snap to the token boundaries" so it "doesn't require pixel-perfect highlighting"; partial-word selections lock in the whole word; double-click selects a single-token entity; a `--highlight-chars` toggle exists for character offsets ([Prodigy NER docs](https://prodi.gy/docs/named-entity-recognition)). Label Studio's Text tag has `granularity = symbol | word | sentence | paragraph` and its NER template tells users to use `word` "to make sure that all highlighted spans ... are complete words" ([Text tag](https://labelstud.io/tags/text), [NER template](https://labelstud.io/templates/named_entity)).
* **Boundaries are a main disagreement source and can be relaxed.** In a Japanese clinical NER study, boundary determination is described as "one of the most common sources of disagreements"; *lenient span* and *point* annotation gave **up to 25 % less annotation time and ~10 % higher agreement** than boundary-strict annotation, at some cost to downstream NER performance ([Andrade, Yada, Aramaki, JMIR Med Inform 2024](https://medinform.jmir.org/2024/1/e59680)). Effects of imprecise boundaries on entity-linking models depend on model and noise ratio ([Andrade et al., ACL 2023](https://aclanthology.org/2023.acl-long.458)).
* **Spans that are "too semantic" generate end-point disagreement.** Prodigy's guidance: if annotators cannot agree on exact end points the category may be too semantic for NER ([Prodigy NER docs](https://prodi.gy/docs/named-entity-recognition)).
* [INFERENCE, Vietnamese] Written Vietnamese separates *syllables* with spaces; whitespace tokens therefore are syllables, and a 3-8 syllable note has only 3-8 tokens. Word-level snapping loses nothing for the quoted example notes (`ve may bay vietjet tet 2tr9`) and removes the pixel-precision problem entirely. Amount tokens (`2tr9`, `420k`) are single whitespace tokens.
* **Offsets pitfall.** JavaScript strings and DOM text `data` are UTF-16 ([MDN String.length](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/length), [DOM Standard "length of a node"](https://dom.spec.whatwg.org/)); Label Studio stores `start`/`end` "in characters" ([Text tag](https://labelstud.io/tags/text)). The quet schema uses code points into NFC text. [INFERENCE] NFC Vietnamese letters are BMP, so UTF-16 units equal code points until an emoji or other astral character appears; convert explicitly, never assume.
* Weak spot: no study I found compares drag vs click-click vs keyboard word-index for **short** (3-8 word) strings.

## 4. One decision per screen vs several decisions on one form

* **Splitting decisions across screens changes the labels.** In a 917-annotator randomized experiment, asking two questions about the same tweet on two screens instead of one shifted hate-speech/offensive-language annotation rates by 5-7 percentage points; asking hate speech first yielded 46.6 % HS / 35.4 % OL, reversed order 39.3 % / 33.8 % ([Kern et al., Findings EMNLP 2023](https://aclanthology.org/2023.findings-emnlp.992.pdf)); [order effects follow-up, UncertaiNLP 2024](https://aclanthology.org/2024.uncertainlp-1.8.pdf) (5-7 pp figure quoted there from earlier work). **Implication:** layout and question order are not neutral; fix them for all collaborators and do not change mid-project.
* **One-question card vs multi-label list on short text (mobile and PC).** FAST (EMNLP 2021 demo), sentiment annotation of ≤50-character Japanese product reviews, 3 annotators per method: mean seconds/annotation: doccano PC 7.3 / mobile 8.3; FAST multi-label UI 5.4 PC / 5.2 mobile; FAST card UI 4.4 PC / 4.7 mobile; accuracy 0.95-0.98 across arms. Authors state the card UI was faster than the multi-label UI (their prose says 18 % mobile / 25 % PC; my arithmetic on the table gives ≈10 % mobile / ≈19 % PC, so read it as roughly 10-25 %) ([Kawamoto et al., FAST](https://aclanthology.org/2021.emnlp-demo.41.pdf)). Small n; the card is a *binary* question (matches / does not match).
* **Binary per-label questions are costly when text must be re-read per question.** For passage labelling the cost per read-through dominates, so a binary design was excluded as "prohibitively" expensive ([Stureborg et al., CHI 2023](https://arxiv.org/pdf/2302.02990), section 3.5).
* **Prodigy rationale** for binary/accept-reject: only press accept/reject; but for manual spans it uses one screen with the label chosen first ([Prodigy NER docs](https://prodi.gy/docs/named-entity-recognition); vendor documentation, not a study).
* **Decomposing a big label set.** Showing a hierarchy in a single pass gave mean F1 0.52 vs 0.46 for a flat list; grouping conceptually similar labels in the same partition gave F1 0.50 vs 0.34 for random partitions; 3 % → 13 % true-positive frequency from pre-filtering raised precision by ~6.7 points ([Stureborg et al., CHI 2023](https://arxiv.org/pdf/2302.02990), section 4; crowd workers, vaccine-concern taxonomy, 24 labels). Exploiting hierarchy/correlation/sparsity cut human computation time up to **6x** versus asking about every label for every image ([Deng et al., CHI 2014](http://ai.stanford.edu/~olga/papers/chi2014-MultiLabel.pdf)).
* [INFERENCE] quet-web's `null_for_types` is a sparsity/gating rule: after the type is chosen, spans forbidden for that type should disappear (or be pre-nulled) so the annotator never sees a decision that does not apply.

## 5. Pre-annotation / suggestions: speed gain is real, anchoring is real

| Study | Design | Speed | Quality / bias |
|---|---|---|---|
| [Lingren et al., JAMIA 2013](https://pmc.ncbi.nlm.nih.gov/articles/PMC3994857) | 2 trained annotators; dictionary pre-annotation of clinical NER; 19,002 entities | **13.85-21.5 %** less time per entity (paired t, p<0.01) | IAA 93.4-95.5 %, no significant difference in IAA or performance vs gold |
| [Mikulová et al., LREC 2022](https://arxiv.org/html/2306.09307v1) | 4 annotators, 8 setups, Czech dependency syntax, high-accuracy parser | From-scratch takes "almost **1.7x**" longer; per-annotator time ranged 50-200 min (pre-parsed) and 130-280 min (scratch) | Accuracy roughly equal (e.g. LAS 95.0 pre-parsed vs 94.5 scratch); agreement higher with pre-annotation. [INFERENCE] the gold was adjudicated from four annotations, half of them pre-parsed, so a circularity risk favours pre-annotation |
| [Berzak et al., EMNLP 2016](https://aclanthology.org/D16-1239.pdf) | 5 trained annotators, 360 sentences; correct parser output vs annotate from scratch | n/a | **Clear anchoring.** Averaged error reduction on parser-based gold vs human gold: 49 % POS, 34 % UAS, 35 % LA, 36 % LAS (i.e. reviewers drift to the tool's output). Blind judges preferred human-based annotation in 56.7-64.3 % of disagreements (5 of 6 cells significant). Where the *two* parsers disagreed, approving the parser's output was much worse (humans preferred 78.7-85.4 %); where parsers *agreed*, no clear loss (51.6-58.5 %). Authors propose a hybrid: review only what several systems agree on |
| [Fort & Sagot, LAW 2010](https://aclanthology.org/W10-1807.pdf) | POS tagging, Penn Treebank, varied tagger accuracy | Even "a not so accurate tagger" improved speed | "Biases do appear and should be taken into account" |
| [Levy et al., CHI 2021](https://vis.csail.mit.edu/pubs/automated-suggestions-impact.pdf) | 18 clinicians, clinical-concept annotation; two aids: recommend labels (top-10 list) vs fully pre-populated spans | Label recommendation: median **3 s vs 6 s** per annotation; 2 s when a correct label was in the list, ~10 s (same as no aid) when only wrong ones were | Fully pre-populated suggestions: experts accepted improper mentions and took less initiative adding annotations |
| [Schroeder, Roy, Kabbara, ACL Findings 2025](https://arxiv.org/html/2507.15821v1) | Pre-registered, 410 crowd annotators, >7,000 annotations, LLM suggestions on subjective labelling | **No speed-up**: NYC baseline 54.3 s vs 66-91 s with suggestions (they added one extra rating question per item) | Annotators "strongly took" suggestions; overlap with LLM labels rose by ≥40 % at the usual 3-of-5 crowd threshold (81-87 % overlap); LLM scores evaluated against those labels inflate |
| [Buçinca et al., CSCW 2021](https://iis.seas.harvard.edu/papers/2021/bucinca21trust.pdf) | N=199, AI suggestion + explanation, simulated 75 %-accurate AI | n/a | "Cognitive forcing" (on demand / update-after-own-answer / 30 s wait) significantly reduced overreliance vs plain explanations, but participants rated those designs *least* favourably; benefits larger for people high in Need for Cognition |
| [Desmond et al., IUI 2021](https://arxiv.org/pdf/2104.04122) | 54 MTurk workers, **21-label** set; model ranks labels, shows top 5 + "View More" | Baseline 9.36 s/trial; assisted 8.81 s (weak) / 9.07 s (strong); trials where "View More" was used: 15.97 s vs 7.89 s | Even a weak model did not reduce human accuracy, no over-reliance observed. Authors warn that unstable/inconsistent ordering hurts since spatial memory of fixed menus speeds search |

Reading across: pre-annotation speeds work (14-40 % in most expert studies, none in the one subjective-task crowd study) and anchoring is documented in every study that tested for it, strongest for subjective labels, for single-system suggestions, and for fully pre-filled answers. Mitigations with evidence: show suggestions only where multiple systems agree (Berzak), ask for the human answer first (Buçinca "update"), recommend instead of pre-fill (Levy, Desmond), and track the acceptance rate [INFERENCE].

## 6. Fatigue, session length, order effects

* **Crowd data say fatigue is smaller than folklore.** Nine million annotations from three longitudinal MTurk datasets: workers were "extremely stable" in quality over long periods; quality in the first five tasks predicted long-term quality ([Hata et al., CSCW 2017](https://arxiv.org/abs/1609.04855v2)). Caveat: self-paced, self-selected, paid microtask workers.
* **Item order matters a little.** In batches of 50 tweets the 50th tweet was ≈2.8 pp less likely labelled hateful and ≈4.5 pp less likely offensive than the first, no positive trend observed ([UncertaiNLP 2024](https://aclanthology.org/2024.uncertainlp-1.8.pdf)).
* **Self-consistency is lower than people assume.** Annotators gave inconsistent responses to re-presented items around **25 %** of the time across four NLP tasks (16 annotators completed both rounds) ([Abercrombie et al., NLPerspectives 2025](https://arxiv.org/html/2301.10684v2)); the authors recommend reporting intra-annotator agreement as quality control.
* Vigilance decrement is a robust phenomenon in monitoring tasks (signal detection over time), but I found no peer-reviewed measurement for *classification-annotation* sessions of under an hour ([general review of the vigilance decrement](https://pmc.ncbi.nlm.nih.gov/articles/PMC8060034)). Blog posts on "annotation fatigue" exist; I treat them as non-evidence.
* Large inter-annotator speed variance: pre-parsed times 50-200 min across annotators ([Mikulová 2022](https://arxiv.org/html/2306.09307v1)) - speed is a poor proxy for quality.
* [INFERENCE] 150 notes × 5-15 s (sections 2, 4, 5) is ~15-40 minutes. Fatigue is not the binding constraint for the gidi pass; resumability and not losing work are.

## 7. Number of choices vs decision time (Hick's law); 8+ classes

* Hick's law: choice reaction time grows with the log of the number of stimulus-response alternatives; the slope falls with practice and with high stimulus-response compatibility, and the law is widely treated as a guide for interface design ([Proctor & Schneider, QJEP 2018 review](https://web.ics.purdue.edu/~dws/pubs/ProctorSchneider_2018_QJEP.pdf)).
* [INFERENCE] 8 options is 3.2 bits (log2(n+1)); going 8 → 4 saves under 1 bit. For *learned, positional* keys the slope shrinks, and the multi-second cost in labelling is semantic discrimination between confusable classes, not selecting a key. I have no source quantifying Hick-slope for annotation; treat as a minor term.
* **More categories lowers agreement.** A meta-analysis of 96 studies / 346 agreement indices found number of categories among seven factors affecting reported agreement, with a negative relationship (partly due to harder-to-distinguish categories); annotator training, and its intensity, raised agreement ([Bayerl & Paul, Computational Linguistics 2011](https://aclanthology.org/J11-4004.pdf); domains were word-sense, prosody, phonetics - extrapolation).
* **How tools handle large label sets.** Digit keys 1-10 then shift/alt modifiers (Prodigy); searchable/shortlist menus: Desmond's top-5 + "View More" was fast when the label was in the shortlist and **slower** when not (15.97 vs 7.89 s per trial); KCAT constrains typing by a knowledge hierarchy to prevent annotators having to memorise thousands of types ([KCAT, ACL 2019 demo](https://aclanthology.org/P19-3017.pdf)); Label Studio can lay choices out as dropdown, inline row or stacked column and can shuffle them ([Choices tag](https://labelstud.io/tags/choices)).
* **Stable positions vs randomized positions.** Desmond et al. argue a consistent display lets spatial memory speed selection. Label Studio offers `randomize` "to reduce position bias" and re-numbers hotkeys to the visible order ([Choices tag](https://labelstud.io/tags/choices)). I found no study quantifying position bias in annotation-label lists, so the tradeoff is unresolved; with 8 options and a *learned key per class*, randomizing would defeat the speed benefit [INFERENCE].
* [INFERENCE] quet-web's 8 types split by money direction: in = income, borrow, repayment_in, refund; out = expense, lend, repayment_out; neutral = transfer. The confusable pairs in the schema are mirror pairs (borrow/lend, repayment_in/repayment_out) and neighbours (income/refund, expense/transfer). Grouping related options is supported by the Stureborg grouping result above.

## 8. Label definitions: inline vs on demand

* **No controlled study found** that compares always-visible definitions to on-demand definitions for annotators. This is the weakest area.
* Related evidence: (a) Stureborg et al. had workers read written definitions in a dedicated micro-task, then 10 tutorial items with corrections and a 3-question entrance exam before real data ([CHI 2023](https://arxiv.org/pdf/2302.02990), section 3.2) but did not isolate the effect of each; (b) training and training intensity increase agreement ([Bayerl & Paul 2011](https://aclanthology.org/J11-4004.pdf)); (c) incomplete or ambiguous label guidelines produce inconsistent labels and are costly to write for crowd workers ([Chang, Amershi, Kamar, CHI 2017 "Revolt"](http://library.usc.edu.ph/ACM/CHI%202017/1proc/p2334.pdf)).
* HCI principle: make options visible, minimise memory load ([Nielsen, heuristic 6 Recognition rather than recall](https://www.nngroup.com/articles/ten-usability-heuristics)).
* Tool practice: Label Studio `Choice` has a `hint` shown on hover ([Choice tag](https://labelstud.io/tags/choice)); Prodigy has an `h` key to show instructions ([web app docs](https://prodigy.ai/docs/api-web-app)). [INFERENCE] hover hints do not exist on touch and are invisible to keyboard users unless also shown on focus.
* [INFERENCE] The gidi `types` definitions run from one sentence to a ~700-character paragraph (`transfer`, with vi-VN heuristics and examples). A paragraph cannot be inline per option on a single card without pushing the record text off the screen. Show the first sentence next to each key (recognition); the rest on demand for the highlighted option.

## 9. Auto-advance, accidental commits, undo

* **No study isolating error rate from auto-advance** (advance on save with no confirmation) was found. Related evidence on speed-accuracy: forcing very fast per-item judgments lowers recall; in rapid-serial-presentation crowd labelling, sentiment went 4.25 s → 0.25 s per item (10x) with recall 0.97 → 0.84 and precision 0.93 → 0.94 *after pooling 5 workers*; at 100 ms image display recall dropped once positives exceeded ~35 % ([Krishna et al., CHI 2016](https://arxiv.org/pdf/1602.04506)). Self-paced advance after an explicit commit key is nowhere near this regime.
* Error-prevention guidance: prevent slips by eliminating error-prone conditions or confirming before commit, prioritise high-cost errors; slips are inattention errors, mistakes are mental-model mismatches ([Nielsen heuristic 5](https://www.nngroup.com/articles/ten-usability-heuristics)). Practical form in tools: **undo** (Prodigy: `backspace`/`del` undoes the last decision, with a history buffer, [docs](https://prodigy.ai/docs/api-web-app)).
* [INFERENCE] When the screen advances automatically, the one irreversible-feeling event is "I thought I saved X but saved Y". The cheap mitigation is a persistent "last saved" line showing the previous record's label with a one-key reopen.
* The existing `Enter` refusal when an applicable span is unmarked is an instance of "check before commit" (section 4 gating) and is consistent with the guidance.

## 11. Mobile / touch

* **Card UI works on phones for short text.** FAST (above): card UI 4.7 s mobile vs 5.2 s multi-label; doccano on mobile was slowest of all arms (8.3 s) ([FAST](https://aclanthology.org/2021.emnlp-demo.41.pdf)). Prodigy ships swipe gestures for accept/reject ([web app docs](https://prodigy.ai/docs/api-web-app)).
* **Workers themselves prefer desktops.** In a survey of 148 MTurk workers, workers "unanimously favor using a desktop to complete and manage crowdwork" and find phones/tablets "marginal at best" ([Dutta et al., 2024](https://arxiv.org/html/2409.04676v1)). A CHI 2022 paper builds a taxonomy of what makes HITs usable on phones but I only read its abstract ([Mobilizing Crowdwork](https://acwio.github.io/pubs/chi2022-mobile-hit-usability.pdf)).
* **Target sizes.** WCAG 2.2 requires pointer targets of at least 24×24 CSS px (AA, [2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)) and recommends 44×44 CSS px ([2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced)).
* No study found on *span selection by touch* in annotation. [INFERENCE] Native touch text-selection handles fight custom drag handlers; tap-start-word then tap-end-word on snapped word chips avoids both.

## 12. Statuses: uncertain / skipped

* Self-reported confidence is informative but unevenly calibrated: some workers are over-confident, some under-confident, some accurate ([Oyama et al., IJCAI 2013](https://www.ijcai.org/Proceedings/13/Papers/376.pdf)). Revolt surfaces "uncertain" items with workers' explanations to find ambiguous concepts ([CHI 2017](http://library.usc.edu.ph/ACM/CHI%202017/1proc/p2334.pdf)). Prodigy treats `ignore` as "I don't know the answer or the question is confusing" and keeps it distinct from accept/reject ([NER docs](https://prodi.gy/docs/named-entity-recognition)).
* [INFERENCE] gidi's schema requires a note on `uncertain`; collecting the note at the moment of choosing `uncertain` is better than a separate step.

## 13. Label Studio's pattern vs the evidence

Label Studio facts below are from its docs: pick a **label first**, then click/highlight text to create a region ("Select the label ... Click the text ... to apply"), regions listed in a **Regions sidebar**, label changes "save automatically" as a draft, **Submit** moves on to the next task, and drafts are visible in a history panel ([Labeling guide](https://labelstud.io/guide/labeling)); `Text granularity="word"` ([Text tag](https://labelstud.io/tags/text)); per-region Choices via `perRegion` ([NER template](https://labelstud.io/templates/named_entity)); `Choice hint` on hover and `randomize` / `layout` on Choices ([Choice](https://labelstud.io/tags/choice), [Choices](https://labelstud.io/tags/choices)).

| Label Studio pattern | Evidence / audit verdict |
|---|---|
| **Labels + Choices in one task, one screen** | **Supported.** Splitting decisions across screens changes labels by 5-7 pp and order changes distributions (Kern 2023, section 4); one-question card was fastest on short text (FAST). |
| **Word granularity for text spans** | **Supported.** Standard in Prodigy and Label Studio; boundary choice is a top disagreement source; whitespace tokens = syllables in Vietnamese (sections 3). |
| **Label-then-highlight (active label is a mode)** | **Conventional but with a known cost; partly contradicted for a fixed 2-field schema.** No study measures it. quet-web's complaint "which field a selection goes to" is the mode-error problem (a hidden current state decides what a gesture does, Nielsen heuristic 5). For a schema with exactly 1-2 named fields, [INFERENCE] a *slot per span* (click/focus the slot, then select words, or select words and the first empty slot takes it) removes the mode. Label Studio needs label-first because its label set is open-ended. |
| **Hotkeys per label / digit hotkeys** | **Supported.** KLM saves ≈1 s per decision versus mouse (section 2); Prodigy uses digits; show the key on the button (Lane 2005). |
| **`randomize` choice order to reduce position bias** | **Contradicted for expert annotators with a fixed, learned key map** (Desmond: stable layout speeds search; Hick slope shrinks with practice). Evidence that position bias is large in annotation is absent. Do not copy. |
| **Region list / Results sidebar** | **Weak.** Useful with many regions per task. With ≤2 spans a region list adds screen area (complaint 1); show the 2 span slots with their text instead [INFERENCE]. |
| **Auto-saved draft + explicit Submit that advances** | **Supports the user's complaint 4 (what is saved).** No study of this directly; Nielsen heuristics on visibility of status/undo apply. The two-state model (draft / submitted) is clear because *advancing is tied to one explicit act*; quet-web's current "Enter / u / s save and advance" is also explicit, so the fix is visible state + last-saved line, not necessarily a Submit button [INFERENCE]. |
| **Hover `hint` for definitions** | **Partly supported** (definitions on demand, recognition principle) but hover is invisible to keyboard and touch users; also show on focus/key. |
| **Relations off** | **Neutral/supported**: not needed for this schema. Neves & Ševa score relation support as a feature only. |
| **Model predictions as pre-filled regions** (standard LS pre-annotation workflow, not read in detail) | **Contradicted for unbiased labelling.** Pre-fill causes the strongest anchoring (Levy, Berzak, Schroeder). quet-web's default `show_proposals: false` is the evidence-backed choice. |

## 14. Well supported vs weak

| Claim | Strength | Why |
|---|---|---|
| Pre-annotation saves time (roughly 14-40 %) in expert annotation | **Well supported** | Lingren 2013, Mikulová 2022, Fort & Sagot 2010, Levy 2021; but one subjective-task crowd study found none (Schroeder 2025) |
| Pre-annotation anchors annotators; pre-filled answers worst | **Well supported** | Berzak 2016, Levy 2021, Schroeder 2025, Buçinca 2021 (different tasks, all same direction) |
| Layout / question order / screen splitting change labels | **Well supported** (one lab, large n) | Kern 2023, UncertaiNLP 2024 |
| Training with examples + definitions raises agreement | **Well supported** | Bayerl & Paul 2011 meta-analysis, Stureborg 2023 protocol |
| More categories = lower agreement | **Moderately supported** | Meta-analysis, different domains |
| Keyboard faster than mouse per decision | **Well supported as motor physics**, **weak as annotation-specific** | KLM numbers; no controlled annotation study |
| Word-snapping beats character precision for speed | **Moderate (practice)**, weak as measured effect | Prodigy/LS defaults; boundary-relaxation study (25 % time) |
| One-question card faster on short text | **Weak-moderate** | FAST, n=3 per arm, binary question |
| Stable label positions beat reordering | **Weak-moderate** | Desmond 2021 (21 labels, crowd) + menu literature |
| Hick's law matters for 8 options | **Weak for this setting** | Law is solid; slope shrinks with practice; semantic confusion dominates |
| Inline vs on-demand definitions | **Not found** | No controlled study; only principles |
| Auto-advance raises errors | **Not found** | Only speed-accuracy results at extreme paces (Krishna 2016) |
| Session fatigue within <1 hour | **Weak / contradictory** | Hata 2017 no decline; small order effects |
| Mobile span selection | **Not found** | Only card-UI classification results |

## 15. Limits of this review

* Could not open full text of: Wang et al., CHI 2024 (Human-LLM collaborative annotation; ACM 403), Gadiraju et al. HT 2017 (task clarity), Lane et al. 2005 beyond abstract-level summaries, Mobilizing Crowdwork beyond its abstract. None of their claims is used.
* Marcus et al. 1993 (Penn Treebank pre-annotation) is only cited second-hand via Berzak et al.
* Most evidence is on crowd workers and long documents; the quet-web population (outside collaborators, 3-8 word notes, 8 classes, 2 spans) has no direct study. Implication 13 proposes measuring it.

## Implications for quet-web

Ranked by (user pain × strength of evidence). "LS" = Label Studio.

1. **Make span marking keyboard-and-click cheap, and remove the "which field" mode.** (Complaints 2, 5.) Show the note as numbered/snapped word chips; two span slots (target, value) sit under it as visible slots; clicking a word range (click start, click end, or type the two numbers) fills the *focused slot* and moves focus to the next empty one; no drag required, drag still allowed. Evidence: KLM (≈1.7 s per drag-mark vs ≈0.5 s for two keys), boundary precision is the main span disagreement source, word snapping standard (Prodigy, LS). *LS comparison:* LS's label-then-highlight is a mode; the evidence neither supports nor measures it, and your complaint is the mode error. Keep LS's word granularity, replace its mode with a slot per field.
2. **Show one visible save state and one visible advance rule.** (Complaint 4.) Two states only: *draft* (unsaved edits) and *saved* (with the saved label shown); a "last saved: <type> · <target> · <value>  [reopen: z]" line after auto-advance; Enter always means "save as complete and go to next". Evidence: Nielsen error prevention/status; no auto-advance error study exists, so keep undo one key and always visible. *LS comparison:* LS's auto-saved draft + explicit Submit matches the user's liking and is the right *concept*; an explicit button is optional here because Enter is already explicit.
3. **Type picker: 8 keys, always visible, key on each button, short gloss on the same line, long definition on demand.** (Complaint 3.) Single row/column of 8 buttons each showing `1 expense - money leaves, no repayment`; stable order, stable digit; full definition for the focused/hovered option via `?` or on focus, never a permanent side panel. Evidence: KLM, Prodigy digit keys, recognition rather than recall, Lane 2005 (show the key), Hick slope shrinks with practice. *LS comparison:* LS Choices + digit hotkeys supported; LS `randomize` contradicted for a fixed expert key map (do not randomize).
4. **Group the 8 types visually by money direction (in / out / neutral) and pair mirror types adjacent.** Evidence: grouping similar labels gave F1 0.50 vs 0.34 for random groups (Stureborg); disagreement concentrates in confusable pairs. [INFERENCE] borrow next to lend, repayment_in next to repayment_out; keep digits stable across projects with the same schema.
5. **Cut the screen to: record text, type buttons, the 1-2 span slots, status keys; everything else behind `?` or a drawer.** (Complaints 1, 6.) A one-question card on short text was fastest (FAST); the long definitions, queue, progress detail and help are not part of the decision. *LS comparison:* LS's Regions sidebar and extra panels are the thing to *not* copy for a ≤2-span schema; keep its single-screen task layout.
6. **Gate by schema, not by error messages.** After type selection, hide or pre-null spans in `null_for_types`; keep the Enter refusal for an unmarked applicable span. Evidence: sparsity/hierarchy gating (Deng 6x time cut), Nielsen error prevention.
7. **Cut the keyboard vocabulary to a small, discoverable core.** (Complaint 5.) Core: `1`-`8` type, `Enter` save complete, `u` uncertain, `s` skip, `Backspace`/`z` undo, `←/→` or `j/k` navigate, `?` help. Move `x n c m [ ] \` and `Tab` slot-switching into explicit visible controls or implicit behaviour (auto-advance to the next empty slot, clicking a slot focuses it, `Esc` clears). Evidence: Lane 2005 (undiscovered shortcuts are not used), Prodigy's small fixed set (a/x/space/backspace/digits). Print the key on every control.
8. **Default to no model proposals; if enabled, use a safer form than pre-fill.** quet-web's `show_proposals=false` default is evidence-backed. If proposals are shown: reveal after the annotator's own choice and show "compare/accept" (Buçinca "update"), show only proposals where ≥2 systems agree (Berzak), never pre-fill type and spans together (Levy, Schroeder), log accept rate per annotator, and hold out a no-proposal subset to measure anchoring [INFERENCE]. *LS comparison:* LS's standard pre-annotation (pre-filled regions) is the form the evidence warns about.
9. **Onboarding calibration before item 1.** Show the 8 definitions once with 2 worked examples per confusable pair, then 6-10 practice items with corrections, before real data. Evidence: training intensity raises agreement (Bayerl & Paul), the tutorial + exam protocol in Stureborg. Cheap for 150 notes, high value for outside collaborators.
10. **Fix layout and order across all collaborators; keep item order from being confounded.** Do not change field order or layout mid-project (Kern 2023: 5-7 pp). Spread strata/review groups through the queue rather than blocking them [INFERENCE], and keep time-per-record, key presses and undo counts per annotator.
11. **Quality probes cheap enough to leave on:** silently repeat ~5-10 % of records to estimate self-consistency (annotators are inconsistent ~25 % of the time, Abercrombie 2025); consider `uncertain` as first-class with an inline note box opened by `u`.
12. **Make state survive interruption.** The pass is ~15-40 minutes [INFERENCE]; resume at the first unlabelled record, autosave drafts, no forced breaks; fatigue evidence is weak (Hata 2017).
13. **Instrument and pilot.** The literature has no study of this exact setup. Log per-record time, keystrokes, undo and re-open rates; run 2-3 collaborators on ~20 notes with old vs new screen before the full queue. Treat any speed difference as meaningful only with such measurement (per-annotator variance is large: 50-200 min on the same task in Mikulová 2022).
14. **Offsets are code points in NFC; the DOM is UTF-16.** Normalise to NFC on load, snap to whitespace tokens, convert every offset explicitly on save. Do not use `Intl.Segmenter` word boundaries for unaccented Vietnamese syllables.
15. **Mobile: low priority; do not break it.** If supported: card layout, ≥44 CSS px type buttons (WCAG 2.5.5), tap-start-word / tap-end-word range selection, no hover-only affordances. Evidence: FAST card UI; crowd workers prefer desktops (Dutta 2024).
16. **Do not randomize option order; do not add a region list; do not add relations.** (Contradicted by evidence/audit for this schema, see section 13.)
